# 테스트 기준 — 무엇을 어떤 크기의 테스트로 지킬지

테스트를 계획할 때 쓰는 기준이다.
판단의 출발점은 질문 하나다: **이 코드가 조용히 틀리면, 누가 언제 알게 되나?** 바로 드러나고 피해가 작으면
따로 테스트하지 않는다. 늦게 드러나거나 피해가 크면 테스트로 지킨다.

## 1. 코드 네 종류와 그 테스트

| 종류 | 알아보는 법 | 테스트 |
|---|---|---|
| **핵심 로직** | 분기·계산·규칙이 많고 바깥 의존이 적다. 파서, 판정 규칙, 상태기계, 숫자·날짜 형식, 알고리즘 | 단위 테스트로 꼼꼼히. 경우가 많으면 표 하나(`parametrize`, `it.each`)로 경계값·스펙의 예외 경우까지 |
| **연결 코드** | 로직은 적고 DB·외부 API·여러 모듈을 이어 붙인다. API 핸들러, 컨트롤러, 워커 진입점 | 단위 테스트를 따로 두지 않고, 그 흐름을 지나는 통합 테스트로 주요 경로와 오류 경로를 짧게 |
| **단순 코드** | 값 전달, 필드 옮겨 담기, getter, 상수, 설정 | 따로 짜지 않는다. 타입 검사와 그 코드를 지나는 위쪽 테스트가 확인한다 |
| **뒤엉킨 코드** | 핵심 로직과 바깥 호출이 한 함수에 섞여 있다 | 먼저 핵심 로직과 연결 코드로 나눈 뒤 위 기준을 따른다. 나누기가 이번 범위 밖이면 통합 테스트로 덮고, 나눌 일을 남긴다 |

## 2. 우선순위를 올리는 조건

종류와 관계없이 아래에 걸리면 테스트를 먼저, 더 꼼꼼히 둔다.

- **피해가 큰 곳**: 데이터 저장·삭제, 권한·보안, 돈, 사용자에게 나가는 결과물.
- **버그가 났던 곳**: 재현 과정(환경·단계·기대 결과·실제 결과)을 그대로 실패하는 테스트로 옮기고, 빨갛게 되는 것을 본 뒤 고친다.
- **자주 고치는 곳**: 변경이 잦을수록 깨질 기회가 많다.
- **약속한 경계**: 다른 모듈·클라이언트·사용자에게 약속한 응답 모양과 동작.

## 3. 테스트 크기 셋

| 크기 | 확인하는 범위 | 쓰는 곳 |
|---|---|---|
| **단위** | 함수·클래스 하나의 동작. 빠르고 안정적이다 | 핵심 로직 |
| **통합** | 두 개 이상의 부품이 실제로 맞물리는지. 일회용 DB 같은 실제 의존을 쓴다 | 연결 코드, 약속한 경계 |
| **E2E** | 사용자가 하는 일을 처음부터 끝까지, 실제 실행 환경에 가깝게 | 서비스의 핵심 사용자 흐름(로그인, 업로드→결과 확인, 결제 같은 것) 하나에 하나씩 |

- 비율은 맞추지 않는다. 크기는 위 1·2절이 정한다. 결과로 단위가 많아지든 통합이 많아지든 괜찮다.
- E2E는 느리고 깨지기 쉬우니 핵심 흐름에만 둔다. 화면 배치·문구 자체보다 다음 동작으로 이어지는지를 단언한다.
- 바깥 경계(네트워크, LLM·외부 SDK, 시계, 파일 저장소)만 가짜로 바꾼다. 내부 협력자를 가짜로 바꿔야만 테스트가 된다면 한 크기 위에서 쓴다.

## 4. 개수와 커버리지

- **테스트 수는 동작 수를 따른다.** 바깥에 약속한 동작 하나에 테스트 하나, 같은 규칙의 여러 경우는 표 하나다.
  함수와 동작은 일대일이 아니다.
- **커버리지는 빈 곳을 찾는 신호다.** 리뷰할 때 바뀐 줄 중 어느 테스트도 지나가지 않는 줄을 찾는 데 쓴다.
  참고치로만 본다(Google: 전체 60% 괜찮음·75% 좋음·90% 아주 좋음, 바뀐 코드 90% 이상). 낮으면 경고다.
- **테스트가 정말 지키는지는 변이로 잰다.** 지키려는 동작을 일부러 깨 보고 테스트가 빨개지는지 본다.
