# 주석 걷어내기

`$finish`의 점검 단계에서 `kit-deslop` 다음에 쓴다.
이 저장소의 팀 지침(`AGENTS.md`)이 주석에 대해 정한 것이 있으면 팀 지침이 이긴다.

## 범위

- 사용자가 파일이나 diff를 주면 그것만 본다. 없으면 기준 브랜치(보통 `main`)와의 diff와 커밋하지 않은 변경을 본다.
- 이번 변경이 더하거나 바꾼 주석과 docstring만 본다.

## 남기는 것

이 목록에 드는 것만 남긴다. 드는지 애매하면 지운다.

- 저장소의 라이선스와 맞는 라이선스·저작권 머리말. 이번 변경이 지어낸 머리말(저장소에 없는 회사·라이선스)은 지우고 보고한다.
- 우리가 바꿀 수 없는 외부 라이브러리·플랫폼·프로토콜 때문에 생긴, 코드만 봐서는 알 수 없는 동작
- 공개 API의 계약(입력·출력·예외)을 적은 docstring. 이름이 `_`로 시작하지 않는 함수·클래스는 공개로 본다.
  구현을 말로 옮긴 docstring은 지운다. 이름과 타입만으로 계약이 드러나지 않으면 계약을 적은 docstring으로 바꿔 쓴다.
- 코드로 나타낼 수 없는 제약을 설명하는 이슈·RFC 링크
- 포매터 지시(`# fmt: off`, `# fmt: on`, `# fmt: skip`)
- 사실로 확인된 우리 코드의 제약("지우지 말 것" 같은 것). 사용자가 정할 때까지만 남긴다. 아래 "지우는 것"의 마지막 항목을 본다.

무시 주석(`noqa`, `type: ignore`)은 여기서 판단하지 않는다. 새로 더하는 것은 키트가 막고,
남아 있는 것은 사용자가 승인한 것이다.

## 지우는 것

주석을 지웠을 때 코드만 읽고도 같은 것을 바로 알 수 있으면 그냥 지운다. 모르게 되면 지우고 **고칠 곳**으로 적는다.

- 코드를 말로 옮긴 설명, 구분선, 주석 처리한 코드, "임시로"·"일단" 같은 변명: 그냥 지운다.
- 우리 코드가 헷갈려서 붙인 설명: 지우고, 그 이름·함수·타입을 고칠 곳으로 적는다. 이름 바꾸기, 함수로 빼기,
  타입으로 나타내기, 구조 바꾸기로 설명 없이 읽히게 하는 것이 목표다.
- 우리 코드의 우회를 정당화하는 긴 주석: 대개 코드가 틀린 것이다. 줄여서 남기지 말고 지우고 고칠 곳으로 적는다.
- "중요", "지우지 말 것", "건드리지 말 것": 주변 코드와 git 기록을 읽어 그 주장이 지금도 맞는지 확인한다.
  가드를 지키라는 주장이면 `kit-deslop`의 상태 판단(호출하는 쪽·타입·완료조건)으로 본다. 정리하는 동안 바뀐 코드가 아니라
  그 상태가 실제로 생길 수 있는지가 기준이다.
  - 틀렸거나 더는 맞지 않으면 지운다.
  - 우리가 바꿀 수 없는 외부 제약이 사실이면 남긴다.
  - 우리 코드에 대한 제약이 사실이면 남겨 두고, 테스트·타입·검사로 옮기자고 보고에 제안한다.
    사용자가 좋다고 하면 옮기고 지운다. 필요 없다고 하면 지운다.

## 순서

1. 주석을 판정한다. 주석이 여러 파일에 많으면 새 서브에이전트에게 판정만 맡겨도 된다. 파일을 고치지 말고 목록만
   내라고 한다. 서브에이전트를 쓸 수 없으면 직접 한다.
2. 지울 주석과 docstring을 지운다. 이 단계에서는 코드를 바꾸지 않는다.
3. 고칠 곳 가운데 작은 것(죽은 경로 지우기, 인자 빼기, 안쪽 이름 바꾸기, 원래 API 쓰기)은 이번 범위 안에서 고친다.
   가드를 지울 때는 `kit-deslop`의 "동작"과 상태 판단을 따른다. 공개 이름 바꾸기는 계약 변경이라 보고만 한다.
   모양을 바꿔야 하면 고치지 않고 보고한다.
   증상을 덮는 가드를 붙여 고치지 않는다.
4. 저장소의 테스트와 린트를 돌린다.
5. 보고한다. 이 스킬이 지운 주석 수(이어진 줄은 하나로 센다), 바꿔 쓴 docstring, 남긴 주석과 이유, 고칠 곳(한 줄씩),
   고친 것, 바뀐 동작, 제약 옮기기 제안, 남은 일을 적는다. 설계 결정의 이유가 주석에만 있었다면 `DECISIONS.md`에 옮긴다.
