# Tidy Tests — 테스트 기준 점검과 계약 테스트 정리

## 개요

기능 하나의 테스트가 **테스트 기준**(`references/test-criteria.md`: 코드 종류마다 맞는 크기의 테스트와 우선순위
조건)대로 짜였는지 점검하고, 쌓인 세분화된 테스트(비계)와 그 사이의 빈틈을 **기능이 약속하는 동작마다 하나씩 있는
믿을 만한 계약 테스트**로 바꾼다. "믿을 만하다"는 느낌이 아니라 증거로 보인다: 계약마다 그 약속을 깨는
변이(일부러 고장 낸 코드)를 만들어 계약 테스트가 전부 잡는 것을 보이고, 비계를 걷어낸 뒤에도 전에 잡히던
변이가 하나도 빠지지 않았음을 보인다.

**철칙 두 개:**
1. **계획을 보여주고 멈춘다.** 1단계는 계획으로 끝난다. 사용자가 승인하기 전에는 테스트 파일을 하나도
   고치지 않는다. "정리해줘"는 1단계를 시작하라는 말이지 수정 승인이 아니다.
2. **계약은 테스트 파일 머리말에 남긴다.** 손댄 테스트 파일마다 머리말(아래 형식)을 쓰고
   `contract_map.py --check`로 확인한다. 머리말이 없으면 끝난 게 아니다.

**용어**
- **계약**: 기능이 바깥(사용자, 다른 모듈, API 소비자)에게 약속하는 동작 하나. "상황·입력 → 관찰 가능한 결과" 한 문장.
- **계약 테스트**: 그 계약을 공개 진입점에서 확인하는 테스트. 같은 규칙의 여러 경우는 표 하나(`parametrize`, `it.each`).
- **비계 테스트**: 만드는 동안 한 걸음씩 확인하던 테스트. 계약 테스트에 포함되면 걷어낸다.
- **변이**: 계약을 깨는 최소한의 코드 변경. 그 계약의 테스트가 잡아야 한다(KILLED).

작업 범위는 대상 레포와 `$S`뿐이다. 다른 프로젝트나 개인 폴더는 열거나 검색하지 않는다.

스크립트는 이 파일 옆 `scripts/`에 있고 `python3`로 실행한다(TS 분석은 `node`). 산출물(실행 결과, 변이 목록과
결과, 판정, 사본)은 모두 레포 밖 스크래치 디렉터리 `$S`에 둔다 — 예: `S=${TMPDIR:-/tmp}$tidy-tests/<레포>`
(Codex 샌드박스에서 쓸 수 있는 위치). 샌드박스가 읽기 전용이면 `$S`에 쓸 권한을 요청한다.

## 언제 쓰나

사용자가 직접 부를 때만 쓴다(`$tidy-tests`). 주로 이런 때다.

- **기능·브랜치를 마친 뒤**: 테스트가 기준대로 짜였는지, 정말 지키는지 확인하고 정리한다.
- **기능을 없앨 때**: 코드, 그 테스트, 머리말의 계약 줄을 함께 지운다. 남은 것은 `inventory.py --src`의
  `covers-test-only-code`(테스트만 쓰는 프로덕션 코드)로 찾는다.
- **아플 때**: 느림, 가끔 실패, 동작을 안 바꾼 리팩터에 깨짐 → 그 기능에 이 흐름을 적용한다.
- **레포 전체 점검**: 가끔, 요청할 때만(아래 "전체 점검").
- 새 기능의 테스트를 처음 쓰는 일은 `tdd`가 같은 기준으로 한다. 실패한 테스트 하나를 고칠 때는 쓰지 않는다.

## 흐름 — 기능 하나씩

### 1단계 — 계약 찾기와 현재 보호 측정 (읽기 전용)

1. **범위와 스냅샷.** 기능 = 프로덕션 진입점 하나와 그것을 확인하는 테스트들.
   `scripts/snapshot.py start <repo> $S/snap.json`. stash·checkout·commit 금지: 작업 트리의 변경은 주인의 작업이다.
2. **격리된 기준선.** 그 테스트들을 기계가 읽는 결과와 함께 돌린다
   (`pytest -p no:cacheprovider --junitxml=$S/x.junit.xml`, `vitest run --reporter=json --outputFile.json=$S/x.json`).
   돌리기 전에 테스트 설정을 읽는다: 기본 `DATABASE_URL`·`REDIS_URL`·저장 경로가 주인의 개발 서비스를
   가리키는 경우가 많으니 일회용으로 돌린다. 샌드박스가 일회용 DB·컨테이너를 못 띄우면 사용자에게 승인을
   요청하고, 그래도 안 되면 그 테스트는 '못 돌림'으로 보고한다(개발 DB로 대신 돌리지 않는다). 끝나면
   `snapshot.py check`로 레포에 새로 쓰인 파일과 브랜치·HEAD 변화를 확인하고, 테스트가 남긴 찌꺼기는 치운다.
3. **계약 목록.** 진입점 코드의 분기·가드·부작용·오류 경로, 문서·ADR, 기존 테스트 이름에서 계약을 뽑는다.
   계약마다 공개 진입점을 실제로 돌려 현재 동작을 관찰한다(스크래치 사본의 일회용 테스트, `-s` /
   `--reporter=verbose`). 의도와 달라 보이는 동작은 미결 질문으로 남기고, 정답으로 고정하지 않는다.
4. **기준 점검.** 진입점과 그 아래 코드를 `references/test-criteria.md`의 네 종류로 나누고, 우선순위 조건에
   걸리는 곳을 표시한다. 단위마다 기준상 있어야 할 테스트(핵심 로직=단위, 연결 코드=통합, 핵심 사용자 흐름=E2E,
   단순 코드=없음)와 지금 있는 테스트를 맞대 본다. 기준상 있어야 하는데 없는 테스트는 빈틈 계약으로 3의 목록에
   더한다. 단순 코드만 확인하는 테스트와 내부 협력자를 가짜로 바꾼 연결 코드의 단위 테스트는 7에서 처리 후보로
   본다. 뒤엉킨 코드는 나눌 후보로 미결 질문에 둔다. 모든 단위가 종류 하나와 판정 하나를 받으면 끝난다.
5. **변이 설계.** 계약마다 그 약속을 깨는 가장 싼 변이 1~3개를 `$S/mutants.jsonl`에 적는다
   (`references/patterns.md`의 "Falsification moves": 가드 삭제, 조건 뒤집기, 필터 제거, 순서 바꾸기…).
6. **현재 보호 측정.**
   `scripts/falsify.py --repo <repo> --mutants $S/mutants.jsonl --out $S/kills-before.json --cwd <dir> -- <그 기능의 테스트 명령>`
   → 계약별 잡힘/안 잡힘 표. 안 잡히는 계약이 빈틈이다. (사본에서만 돌고, 파일이 실제로 로드되는지 먼저 확인하고, 복구·검증한다.)
7. **기존 테스트 분류.** `scripts/inventory.py <테스트> --src <프로덕션> --results <결과> --out $S/inv`로 목록을
   뽑고, 테스트마다 어느 계약에 속하는지와 처리(아래 규칙)를 `$S/verdicts.jsonl`에 근거(`file:line`)와 함께 적는다.
   인벤토리 플래그는 읽을 곳을 알려주는 힌트일 뿐이다. 프로젝트의 TypeScript가 JS API 없는 7.x면, 스크립트가
   알려주는 대로 `$S`에 TS 5를 설치해 쓴다 — 다른 프로젝트의 설치본을 찾아 디스크를 뒤지지 않는다.
8. **계획을 보여주고 멈춘다.** `scripts/verdicts.py $S/inv.jsonl $S/verdicts.jsonl`이 exit 0이어야 한다(모든 테스트가
   처리 하나씩). 보여줄 것: 기준 점검 표(코드 단위 | 종류 | 기준상 테스트 | 지금 있는 테스트 | 판정), 계약 목록과
   현재 보호 표, 새 계약 테스트 설계(진입점, 표의 행, 단언 —
   `references/contract-tests.md`), 흡수·삭제될 테스트와 이유, 미결 질문, 예상 전후(테스트 수, 잡히는 변이).
   주인이 테스트를 잘 몰라도 읽고 판단할 수 있게 쓴다:
   - 맨 앞에 용어 한 줄씩(계약, 변이, 유지·흡수·삭제·수정·미결).
   - 계약마다 쉬운 말 한 줄: 이 약속이 깨지면 사용자에게 무슨 일이 생기는지, 지금 테스트가 왜 그걸 못 막는지.
   - 빈틈을 채우는 새 계약 테스트는 기본으로 넣자고 추천한다. 질문으로 남기는 건 비용이 큰 것(느림, 외부
     서비스 필요)과 제품 의도가 불분명한 것뿐이다.
   승인을 묻는다.

### 2단계 — 계약 테스트로 바꾸기 (승인 후)

1. **계약 테스트를 먼저 쓴다.** 현재 코드에서 통과해야 한다. 실패하면 계약과 현재 동작이 다른 것이니 멈추고
   보고한다 — 버그인지 계약이 틀렸는지는 주인이 정한다.
2. **계약 테스트만으로 변이를 잡는지 확인한다.**
   `falsify.py --mutants $S/mutants.jsonl --out $S/kills-new.json -- <계약 테스트만 실행하는 명령>` → 모든 계약의 변이가 잡혀야 한다.
   안 잡히면 계약 테스트를 강화한다(입력, 단언).
3. **비계를 걷어낸다.** 고유한 단언·경우는 먼저 계약 테스트로 옮긴다. 핵심 로직(파서, 계산, 상태기계)의
   단위 테스트는 기준대로 남긴다 — 머리말에서 그 계약에 묶는다.
4. **보존 증명.** 남은 테스트 전체로 다시 돌려 `--out $S/kills-after.json`, 그리고
   `falsify.py --compare $S/kills-before.json $S/kills-after.json` → 보호 손실이 없어야 한다. 손실이 있으면
   되돌리거나 이유를 적어 승인받는다.
5. **머리말.** 계약 → 테스트. `contract_map.py --check <손댄 파일>`, `snapshot.py check`.
6. **보고.** 전후 테스트 수·LOC·실행 시간, 계약별 잡힌 변이(전 → 후), 남은 빈틈과 미결 질문. 숫자와 함께,
   이제 어떤 동작이 새로 지켜지는지를 쉬운 말로 적는다. 다음 기능은 다시 승인 후.

## 기존 테스트 처리 규칙

| 처리 | 조건 |
|---|---|
| **유지 (Keep)** | 그 자체가 계약 테스트다, 또는 계약 테스트가 대신하기 어려운 까다로운 순수 로직이다. |
| **흡수 (Combine)** | 계약 테스트의 한 경우(표의 행)나 단언으로 옮길 고유한 것이 있다. 고유한 것이 하나라도 있으면 삭제가 아니라 흡수. |
| **삭제 (Remove)** | 계약 테스트가 같은 변이를 잡는다(증명) — 또는 지킬 계약이 없다: 호출처 없는 코드(`grep` + `git log -S`), 타입이 이미 보장하는 사실, 없앤 기능. |
| **수정 (Repair)** | 계약은 맞는데 그 이유로는 실패할 수 없는 단언(약함, 엉뚱한 원인, 공허). 계약 테스트로 다시 쓰며 고친다. |
| **미결** | 판정을 가를 질문. 제품 의도(없앤 기능, 어느 동작이 맞는지, 아직 연결 안 된 코드)는 주인이 정한다. |

- 기준상 단순 코드만 확인하는 테스트는 삭제 후보다. 그 동작을 지나는 위쪽 테스트가 같은 변이를 잡는 것을
  보인 뒤 지운다.
- 경계 mock(HTTP 클라이언트 래퍼, LLM·SDK, 시계, 파일시스템, 브라우저 API)은 괜찮다. 콜백 props는 컴포넌트의
  출력이다. 내부 협력자를 mock하고 있다면 계약 테스트는 한 층 위에서 쓴다.
- 얇은 클라이언트가 보내는 URL·메서드·본문은 와이어 계약이다(서버는 이름이 틀린 필드를 조용히 무시하곤 한다).
  상대편이 정말 그 형태를 받는지도 확인한다.
- 동작을 바꾸지 않는 변이(동치 변이)는 잡을 수 없다 — 이유를 적고 목록에서 뺀다. 그 외의 이유로 변이를 빼지 않는다.
- 느리다는 것만으로는 이유가 안 된다. 기존 실패는 발견 사항이지, 초록을 만들려고 지울 대상이 아니다.

## 계약 머리말

각 테스트 파일의 첫 줄들(docstring 또는 주석). 함수 이름이 아니라 사용자의 말로 쓴 동작.

```python
"""수업 녹음 업로드 (POST /recordings, worker transcribe)

계약:
- 녹음을 올리면 대본 작업이 큐에 들어가고 상태가 queued가 된다 → test_upload_enqueues_transcription
- 300MB를 넘으면 413, 파일은 저장되지 않는다 → test_rejects_oversized_recording
- STT 키가 없으면 실패 상태와 이유가 남는다 → test_missing_stt_key_marks_failed
- 쉬는 시간 구간은 대본에서 빠진다
"""
```

TypeScript는 `//` 줄을 쓰고, 테스트 제목의 고유한 앞부분을 따옴표로 적는다:
`- 멈추면 남은 조각까지 올린다 → "stopping uploads"`. `→`가 없는 줄은 아직 테스트 없는 계약(아는 빈틈)이다.
`contract_map.py <테스트>`가 전체 지도를 출력하고, `--check`는 더 이상 없는 테스트 이름과 머리말 없는 파일에서
실패한다(`--strict`는 어느 계약에도 안 묶인 테스트에서도).

## 전체 점검 (가끔, 요청할 때)

레포 전체를 볼 때는 프로덕션 책임 단위로 나눈다. 하위 에이전트를 쓸 수 있으면 읽기 전용 에이전트마다
`references/audit-brief.md`를 주고 스크래치 사본과 일회용 서비스를 따로 쓰게 한다. 없으면 책임 단위로 하나씩
차례로 진행한다. 결과는 기능별 계획이 되고, 적용은 위 2단계를 기능 하나씩 승인받아 진행한다.

## 위험 신호 — 멈출 것

| 생각 | 실제 |
|---|---|
| "이 정리는 뻔히 안전하니 그냥 적용하자." | 계획이 먼저다. '뻔히 안전한' 삭제가 마지막 남은 가드를 지운다. |
