이 스킬이 끝나기 전에는 구현 코드를 쓰지 않는다.

1. README, `notes/requirements.md`, `notes/design.md`를 열고 관련 코드를 읽는다. 설계 범위는 과제 전체다.

2. `notes/design.md`의 칸을 채운다. 구조는 모양이 다른 안을 둘 이상 놓고 고른 뒤 고른 이유와 버린 안을 적는다. 완료 기준: 빈 칸이 없고, 쓸모없는 칸은 "해당 없음"과 이유를 적었다.

3. 사용자에게 설계를 열 줄 안으로 설명한다: 무엇을 어떤 구조로 만드는지, 입력이 어디로 들어와 어디를 지나 무엇으로 나가는지.

4. **핵심 질문을 만든다.** 이번 설계에서 사용자가 틀리게 이해하면 크게 되돌려야 하는 지점을 찾아 질문 세 개에서 다섯 개를 만든다. 정해진 목록은 없다. 이 프로젝트의 실제 이름과 값을 넣어 묻는다. 아래에서 이 설계에 중요한 것을 고른다.
   - 왜 이 구조인가, 버린 안은 어떤 조건에서 더 나은가
   - 데이터가 어디서 어떤 모양으로 바뀌는가
   - 각 계층이 맡는 책임과 맡지 않는 책임은 무엇인가
   - 바뀌는 상태는 누가 소유하고 누가 바꾸는가
   - 실패하거나 같은 요청이 다시 오면 어떻게 되는가
   - 무엇을 어떤 테스트와 측정으로 확인하고, 무엇은 확인하지 못하는가
   - 일부러 안 만드는 것은 무엇이고 왜인가

   질문은 사용자가 설명해야 답할 수 있게 쓴다. "왜", "어떻게", "~하면 무슨 일이 일어나는가"로 묻고, 구체적인 상황을 하나 준다. 질문 안에 답을 넣지 않고, 예/아니오로 끝나는 확인 질문은 쓰지 않는다.

5. 질문을 하나씩 내고 사용자의 말을 기다린다.

6. 답을 `notes/design.md`와 대조한다. 맞으면 다음 질문으로 간다. 틀리거나 빠졌으면 그 부분만 짧게 설명하고 같은 내용을 다른 말로 다시 묻는다. 사용자가 더 나은 구조를 내면 문서를 고치고 4번으로 돌아간다.

7. 모든 질문을 사용자가 자기 말로 답한 뒤 승인을 묻는다. 승인하면 `notes/design.md` 맨 위의 상태를 "승인됨"으로 바꾼다.

8. 보고한다: 승인한 구조 세 줄, 질문하며 고친 곳, 다음 단계 `$to-tickets`.
