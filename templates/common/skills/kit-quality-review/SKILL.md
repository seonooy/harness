# 코드 품질 리뷰

지금 브랜치의 변경(기준 브랜치와의 diff와 커밋하지 않은 변경)을 본다. 동작이 맞는지보다 구조가 나아졌는지를 본다.
`kit-change`의 리뷰 단계가 큰 변경에 부른다.

리뷰를 시작하기 전에 두 파일을 연다.

- `.ai/project/architecture.md`: 로직의 제자리와 패키지 규칙
- `.agents/skills/kit-change/design-red-flags.md`: 모양 경고 목록

## 기본 질문

> 동작은 그대로 두고 이 변경을 훨씬 단순하게 짤 수 있나? 추상화와 모듈 나누기를 낫게 하고, 엉킨 코드를 줄이고,
> 짧고 읽기 쉽게 만든다. 코드베이스 일부를 다시 짜야 분명히 나아지는 길이 있으면 그 길을 낸다.
> 철저하게 본다. 두 번 재고 한 번 자른다.

## 기준

0. **구조를 과감하게 줄인다.** "조금 더 깔끔하게"에서 멈추지 않는다. 분기·헬퍼·모드·조건문·계층이 통째로
   사라지는 재구성("code judo")이 대개 있다고 보고 찾는다. 복잡함을 옮기기보다 지우는 길을 민다.
1. **1000줄 미만이던 파일을 1000줄 넘게 키우지 않는다.** 넘기면 먼저 나눌지 묻는다. 나눌 수 없는 분명한 이유가 있고
   파일이 여전히 잘 정리되어 있을 때만 넘어간다.
2. **엉뚱한 곳에 분기를 끼우지 않는다.** 상관없는 흐름에 들어간 if, 특수 경우, 일회성 분기는 모양 문제가 아니라
   설계 문제다. 전용 함수·상태 머신·정책 객체·모듈로 뺀다.
3. **돌아가는 코드로 만족하지 않는다.** 동작이 같고 구조가 더 깔끔해지면 그쪽을 택한다. 복잡함을 여기저기로
   나누는 정리보다 움직이는 부품을 없애는 단순화를 고른다. 기존 코드의 습관은 기준이 아니다.
4. **단순하고 지루한 코드를 고른다.** 깨지기 쉽거나 마법 같은 동작, 단순한 데이터 모양을 숨기는 일반화,
   한 겹 감싸기만 하는 함수, 그대로 넘기는 층을 지적한다.
5. **타입과 경계를 분명히 한다.** 필요 없는 `Optional`, `Any`, `cast()`, 모양을 짐작해 쓰는 `dict`를 묻는다.
   dataclass·TypedDict·pydantic 모델처럼 분명한 타입을 쓴다. 조용한 fallback이 불분명한 불변식을 덮으면
   경계를 드러내게 한다.
6. **로직은 제자리에 둔다.** 기능 로직이 공용 경로로 새거나 구현 세부가 API로 새면 지적한다. 이미 있는 헬퍼를
   다시 만들지 않는다. 제자리는 연 `architecture.md`의 패키지와 규칙으로 판단한다.
7. **이유 없이 순서대로 돌리거나 반쯤 적용될 수 있는 갱신을 지적한다.** 서로 기대지 않는 일은 따로 돌리고,
   함께 바뀌어야 하는 상태는 한 번에 바뀌게 한다. 작은 성능 최적화에 매달리지는 않는다.

변경을 `design-red-flags.md`의 항목마다 거른다.

## 물을 것

- 이 변경을 훨씬 단순하게 만드는 재구성이 있나? 개념·분기·헬퍼 층이 줄도록 다시 짤 수 있나?
- 정리했다면서 읽는 사람이 머리에 담을 개념 수는 그대로인가?
- 되풀이되는 조건문이 빠진 모델이나 헬퍼를 가리키나?
- 이 추상화는 제값을 하나, 그냥 감싸개인가?
- 캐스팅·`Optional`·임시 `dict`가 진짜 불변식을 가리나?
- 이 로직이 맞는 파일과 계층에 있나? 응집돼 있던 모듈이 더 얽히거나 상태가 늘었나?

## 보고

중요한 순서로 적는다.

1. 구조가 나빠진 곳
2. 놓친 큰 단순화(code judo)
3. 엉킨 분기가 늘어난 곳
4. 경계·추상화·타입 계약 문제
5. 파일 크기와 나누기
6. 모듈과 추상화
7. 가독성

걸린 설계 경고와 아키텍처 규칙은 이름을 붙인다. 예: `design-red-flags: 그대로 넘기는 함수`, `architecture: app-layers`.
걸린 것이 없으면 "설계 경고·아키텍처 규칙: 걸린 것 없음"이라고 적는다.

큰 구조 문제가 있으면 자잘한 지적을 늘어놓지 않는다. 확신 있는 지적 몇 개가 긴 목록보다 낫다.
구조 문제를 이름 바꾸기 같은 작은 지적으로 덮지 않는다. 같은 생각을 조금 깔끔하게 다듬은 것으로 만족하지 않는다.

## 통과 기준

동작이 맞다는 이유만으로 통과시키지 않는다. 아래는 분명한 이유가 없으면 막는다.

- 더 단순한 재구성이 보이는데 쓸데없는 복잡함을 그대로 둔 변경
- 1000줄 미만 파일을 1000줄 넘게 키운 변경
- 기존 흐름에 일회성 분기를 끼워 엉키게 한 변경
- 공용 코드 여기저기에 기능 검사를 흩어 놓은 변경
- 필요 없는 추상화·감싸개·캐스팅으로 설계를 에둘러 만든 변경
- 이미 있는 헬퍼를 다시 만들었거나, 제자리가 분명한데 다른 계층에 둔 변경

## 고치기

리뷰는 고칠 거리를 찾는 일이다. 이번 범위 안이면 고치고 `kit-verify`로 다시 검증한다.
범위 밖이면 고치지 않고 제안으로 보고한다(`kit-change`의 중단 임계값).

## 말투

직접적이고 진지하게 쓴다. 무례하지 않되 큰 유지보수 문제를 가벼운 제안으로 낮추지 않는다.
변경이 코드베이스를 더 지저분하게 만들면, 또 큰 단순화를 놓쳤으면 그렇다고 분명히 말한다.
