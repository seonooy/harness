# 변경 절차

프로젝트 지침(`AGENTS.md` 또는 `AGENTS.override.md`)과 그 "Checks" 절을 먼저 따른다.

흐름: 완료조건 → 코드 읽기 → 경계·설계 확인 → (계약·데이터·판정이 바뀌면) 테스트 계획 승인 → 구현
→ 정리(`kit-deslop`, `kit-no-comments`) → 검증(`kit-verify`) → 리뷰(큰 변경은 `kit-quality-review`) → 보고·규칙 제안

**명세·티켓으로 구현할 때**(Matt Pocock `$implement`, `$implement-spec`)도 이 절차를 따르고, 세 곳만 이렇게 한다.

- 4단계 테스트 계획: 명세의 Testing Decisions와 `$to-spec`에서 합의한 seam이 승인이다. 다시 묻지 않는다.
  명세에 없는 계약·데이터·판정을 바꿔야 하면 구현하기 전에 멈추고 보고한다.
- 8단계 리뷰: 그 흐름이 부르는 `code-review`로 한다(`$implement-spec`은 통합 브랜치에서 한 번). 큰 변경이면
  `kit-quality-review`의 기준도 함께 본다.
- 10단계 커밋: 그 흐름이 끝에 하는 커밋은 요청받은 커밋이다. push는 요청받을 때만 한다.

1. `.ai/project/intent.md`(프로젝트가 왜 있는지)를 연다. 목표를 관찰할 수 있는 입력→출력으로 적는다.
   예: 파일을 올리면 분석 요청이 저장되고, 같은 ID로 조회된다. 목표가 intent의 "하지 않을 것"이나 "중요한 제약"에
   걸리면 구현하기 전에 사용자에게 말한다. 계획과 이미 구현된 사실을 구분한다.
   - **완료조건**은 실행할 수 있는 확인으로 적는다. 새 테스트, 기존 테스트, `check` 명령 중 무엇이 통과하면
     끝인지 적는다. "잘 동작한다" 같은 말로만 된 완료조건은 쓰지 않는다.
   - **중단 임계값**도 적는다. 기본은 이렇다: 같은 실패를 3번 고쳐도 그대로이거나 정한 경계 밖을 바꿔야 하면,
     멈추고 원인과 선택지를 보고한다.
   - 명세·티켓 없이 시작한 작업이 지침 "Checks" 절의 `to-spec` 줄에 해당하면, 구현하기 전에 그 줄대로 권하고
     답을 기다린다. 거절하면 이 절차대로 이어 간다.
2. 관련 코드와 테스트를 읽는다. 바꿀 함수의 호출자와 테스트부터 본다.
3. `.ai/project/architecture.md`를 열고 바꾸는 경계를 확인한다. 어느 모듈이 무엇에 의존해도 되는지,
   어떤 규칙이 `[검사]`이고 어떤 것이 `[리뷰]`인지 본다. 결과를 "경계: 규칙 안(<규칙 id>)" 또는
   "경계: 바꿔야 함(<규칙 id>, 이유)" 한 줄로 적고 10단계 보고에 넣는다. 4단계 승인을 받으면 표 위에도 적는다.
   바꿔야 하거나 문서에 없는 구조 결정이 필요하면 구현하기 전에 사용자에게 묻고, 정해지면 `architecture.md`에 적는다.
   결정을 지어내지 않는다.
   - 새 모듈·공개 인터페이스를 만들거나 모듈 경계를 바꾸면, 구현하기 전에 함수 이름·인자·반환 타입부터 적는다.
     모양이 다른 안을 두 개 적고, `.agents/skills/kit-change/design-red-flags.md`를 열어 항목마다 두 안을 걸러 고른다.
     안마다 시그니처 몇 줄이면 된다. 두 안과 고른 이유(걸린 경고)는 10단계 보고에 넣는다.
   - 패키지의 아키텍처 스타일이나 패키지 사이 관계를 정하거나 바꿔야 하면 `kit-architecture`를 따른다.
4. **계약·데이터·판정이 바뀌면** 구현하기 전에 `kit-verify`의 design으로 테스트를 계획하고 사용자 승인을 받는다.
   - 계약: 다른 코드나 사용자가 기대는 겉모습. 공개 API의 경로·요청·응답, 함수 시그니처, CLI, 메시지 형식
   - 데이터: 저장되는 것의 모양. DB 스키마·마이그레이션, 파일·캐시 형식, 저장된 데이터를 읽는 방식
   - 판정: 결과를 고르는 규칙. 점수·임계값·분류·매칭·정렬 기준, 권한 판정
   - 셋 다 아니면(버그 수정, 내부 정리, 문구) 승인 없이 진행하고, 보고에 "테스트 계획 승인: 해당 없음"과
     그 이유를 적는다.
   - 승인된 계획이 바뀌면 다시 승인받는다.
5. 테스트를 쓰기 전에 `tdd` 스킬을 연다(스킬로 부를 수 없으면 `~/.agents/skills/tdd/SKILL.md`를 읽는다).
   그 원칙대로 합의한 경계(seam)에서 한 번에 테스트 하나씩 red → green으로 간다. 둘 다 없는 환경이면 이 단계의 규칙만
   쓰고 10단계 보고에 "tdd 스킬 없음"을 넣는다.
   - 실패해야 한다고 계획한 테스트는 구현하기 전에 돌려 red를 본다. 돌린 명령과 실패 줄(테스트 이름과 실패 한 줄)을
     10단계 보고에 넣는다.
   - 구현하기 전에 `.ai/project/rules.md`를 연다. 그 변경 규칙을 지키며 기존 계층과 인터페이스 안에서 작게 구현한다.
     작업 중에는 `check.py fast`로 확인한다.
   - 데이터 모양부터 정한다. if/else에 가지를 하나 더 붙이기 전에 상태 머신·타입 모델·표 같은 자료구조가 맞는지 본다.
     지금 모양이 단순하고 더 자라지 않을 것이면 그대로 둔다.
   - 가장 작은 diff로 해결한다. 더하기 전에 죽은 코드와 겹치는 검증부터 지운다.
   - 검증·예외 처리는 입력 경계(HTTP·CLI·설정·파일·외부 API)에서 한 번 한다. 외부 데이터는 거기서 타입으로 바꾸고,
     안쪽에서는 타입을 믿고 다시 검사하지 않는다.
   - 버그는 증상이 보인 곳이 아니라 처음 잘못된 곳에서 고친다. 생기면 안 되는 상태를 가드·재시도·예외 삼키기로 덮지 않는다.
   - 한 곳에서만 부르는 감싸개, 인자를 그대로 넘기는 층, 같은 일을 하는 두 번째 방법을 만들지 않는다.
6. **정리한다.** 테스트가 통과하면 `kit-deslop`으로 군더더기 코드를, 이어서 `kit-no-comments`로 주석을 걷어낸다.
   두 스킬이 적은 "바뀐 동작"과 넘긴 것은 10단계 보고에 옮긴다. 문서·설정만 바뀌었으면 건너뛴다.
7. `kit-verify`의 verify로 검증한다. 실패하면 원인을 고치고 같은 검증을 다시 돌린다.
   중단 임계값에 닿으면 멈춘다. 검사를 약하게 만들어 통과시키지 않는다.
8. 여러 모듈에 걸치거나 새 모듈·공개 인터페이스를 만드는 변경, 계약·저장·재시도처럼 중요한 변경은 리뷰를 받는다.
   읽기 전용 리뷰어에게 목표, diff, 검증 결과를 보이고 `kit-quality-review`의 기준으로 보게 한다.
   리뷰어 역할을 쓸 수 없으면 그 기준으로 직접 다시 읽고, 리뷰를 맡겼다고 말하지 않는다.
   리뷰 지적도 필요하면 고치고 다시 검증한다.
9. 최종 diff에서 요청 밖 변경과 개인 파일(`.ai/`, 개인 지침, `.codex/` 설정)이
   섞였는지 확인한다.
10. 보고한다. 완료조건의 결과, 무엇이 동작하고 무엇이 스텁·미검증인지 적고, 앞 단계가 보고에 넣으라고 한 것을 모두 적는다.
    - 5단계: 테스트마다 red를 본 명령과 실패 줄(회귀 방지용은 "회귀 방지"), tdd 스킬을 못 썼으면 그 사실
    - 3단계: 경계 한 줄, 두 안과 고른 이유(해당할 때)
    - 6단계: 정리의 "바뀐 동작"과 넘긴 것
    - 8단계: 리뷰를 한 방법. 리뷰어, 직접 다시 읽음, 해당 없음 중 하나와 그 이유
    commit·push는 요청받았을 때만 한다.
11. **배운 것을 규칙으로 올린다.** 리뷰 지적, 같은 실수의 반복, 사용자의 정정에서 문서에 없던 규칙이 보이면
    보고 끝의 "규칙 제안"에 한 줄씩 적는다.
    - 기계로 잡을 수 있으면 검사로 올리자고 제안한다. 예: import 방향은 import-linter 계약, 금지 API는 Ruff TID251.
    - 아니면 `.ai/project/rules.md`나 `architecture.md`에 넣을 문장을 제안한다.
    - 더는 필요 없거나 아무도 지키지 않는 규칙은 걷어내자고 제안한다.
    - 패키지의 스타일을 바꾸자는 신호(`kit-architecture`의 "언제 쓰나")가 보이면 `kit-architecture`로 제안한다.
    - 사용자가 받아들인 것만 고친다. `.ai/checks/`의 설정은 보호 파일이라 제안(`.ai/proposals/`)으로 만들고 사용자가
      `harness.py proposal apply`로 적용한다.

5단계의 구현 원칙과 설계 경고 목록의 출처: `SOURCE.md`
